# Transactions: JSM/Jira ticket, transaction ID and mandatory fields

A **transaction** is anything the operator submits that creates, changes or removes something: provisioning a user, and adding, editing or removing roles.

- **A JSM/Jira ticket is mandatory on every transaction.** Every journey that submits a transaction asks for the ticket and will not submit without it. Send it with the request. The backend is the authority on whether it is valid.
- **Ticket format (decided):** `ITS-` followed by six digits, for example `ITS-123456`. The operator may type just the six digits, but **the UI always sends the full form** (`ITS-123456`) as `jiraTicketId`, and shows the full form on the result page. The one check, and the words used to ask for the ticket (`ticketCopy`), are in `src/services/jiraTicket.ts`: use them in every journey and never write a second pattern. Both journeys ask for just the six numbers, check them as they are typed, and keep Submit unavailable until they are valid. It is a convenience check only; the backend decides whether the ticket is valid.
- **The transaction ID is separate from the ticket.** The backend generates a unique `transactionId` for each transaction and returns it. Where a result page shows a reference (the User Role Manager's does), show the transaction ID as its own item, next to the ticket. Never show the ticket as the reference, and never make up or change a transaction ID in the UI.
- **User Provisioning result pages (from the design):** they show who was or was not provisioned, in which environment, and on success the new user's x number from the backend's reply (`userXNumber`, mocked until the backend defines it; the sentence is left out when it is missing). They do not show the transaction ID or the ticket, and the failure page shows a plain-English reason, never a raw server message. Showing either result discards every answer in the journey, so the browser's Back button starts again at an empty user type step.
- **Mandatory User Provisioning fields:** first name, surname, email address, user identifier (a u, z or c number, or a GAKWO number for NatureScot), job title and location. A request is never submitted with any of them missing. The manager's x number is also sent on every request, but the operator may leave it blank (see below).
- **External user flows live in User Role Management only.** The User Provisioning journey is for internal users and never offers an external user.
- **The mock API follows the same rules:** `src/mocks/handlers.ts` rejects a transaction with a missing ticket or mandatory field (`400`) and returns a transaction ID that is not the ticket. Keep it that way when adding a new transaction.
- **User Role Manager identifier (from the design):** the format depends on the user type chosen. **Public** users enter a username of 4 to 20 letters, numbers, full stops, underscores or hyphens. **Every other user type** enters an x number: `x` and six digits (`x111111`, either case). Spaces, control and invisible characters are rejected for both. Checked in `src/pages/role-manager/validateIdentifier.ts` as a convenience only; the backend decides whether the user exists.
- **User Provisioning identifier (decided):** the format depends on the user type chosen. **Scottish Government and Scottish Forestry** users enter `u`, `z` or `c` and six digits (`u111111`, either case) and are looked up. **NatureScot** users are identified by `GAKWO` and six digits (`GAKWO111111`, either case). The value is sent as typed, trimmed. Checked in `src/pages/provision/validateUserIdentifier.ts` as a convenience only; the backend decides whether the user exists.
- **NatureScot user information (from the design):** NatureScot users are not looked up. On the "Enter NatureScot user information" step the operator pastes one CSV line: first name, last name, email address, GAKWO number, manager's x number (may be blank), an unused value, job title, location (a trailing comma is allowed; values cannot contain commas). The one check is `src/pages/provision/natureScotCsv.ts`, a convenience only. Next stays unavailable until the line is valid. On Next, the UI asks the backend whether the user already exists in FutureDatabase (`checkExistingUser`, temporary contract): if so it stays on the step and says "The user already exists in <environment name>, x number is <x number>"; if not, the review step opens with the pasted details, manager's x number and location filled in. A pasted location is used only if it is on the loaded list (matched ignoring letter case); otherwise the operator chooses one.
- **Manager's x number (decided):** typed by the operator on the "Review your selection before submitting" step, and optional. When given it must be `x` and six digits (`x111111`, either case), checked as it is typed. When left blank, the UI sends the word `dummy` (`DUMMY_MANAGER_X_NUMBER`) and shows it on the ticket step. Any manager number that comes back with the user's record is ignored: it is not shown, pre-filled or sent. The one check is in `src/pages/provision/managerXNumber.ts`, a convenience only.
