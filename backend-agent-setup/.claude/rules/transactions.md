# Transactions: JSM/Jira ticket, transaction ID and mandatory fields

A **transaction** is any request that creates, changes or removes something: provisioning a user, and adding, editing or removing roles, in both User Provisioning and User Role Management. Reads are not transactions.

## JSM/Jira ticket (mandatory on every transaction)

- **Every transaction must carry a JSM/Jira ticket.** A request with a missing, empty or blank ticket is a `400` validation error. Never default it, generate it or skip the check for any role.
- Store the ticket with the transaction record in the Futures Database and include it in every audit record for that transaction (`ticketId`).
- One ticket may cover several transactions, so the ticket is never unique and never a key.
- The ticket's exact format, and whether it is checked against JSM, are still open: see `docs/open-questions.md`. Until decided, validate only that it is present.

## Transaction ID (separate from the ticket)

- **Every transaction gets its own unique transaction ID, generated by this API.** Never accept it from the client, and never use or derive it from the JSM/Jira ticket.
- Return it in the response as `transactionId`, store it with the transaction record and include it in every audit record for that transaction.
- It is not the correlation ID either: the correlation ID traces one HTTP request, the transaction ID identifies the business transaction.
- Its format is still open: see `docs/open-questions.md`. Keep generation in one place so the format is easy to change.

## Mandatory User Provisioning fields

A provisioning request must contain all of these. Any that is missing or blank is a `400` validation error naming the field:

| Field | Meaning |
|---|---|
| `firstName` | First name |
| `surname` | Surname |
| `email` | Email address |
| `userIdentifier` | The user's identifier: a U, Z or GAKWO identifier |
| `managerXNumber` | The X number of the user's manager |
| `jobTitle` | Job title |
| `location` | Location |

- `userType` (see `user-classification.md`) and the JSM/Jira ticket are also required.
- Use Bean Validation on the request DTO; never rely on the UI's checks.
- The exact formats of the U, Z, GAKWO and X identifiers are still open: see `docs/open-questions.md`. Do not invent a pattern.

## External users

**External user flows live in User Role Management only.** User Provisioning never creates or changes an external user.
