# Application Access Hub: backend

The Spring Boot API for Application Access Hub, an internal application for:

- **User Provisioning**: giving an internal user access (Government, Forestry or Nature user types).
- **User Role Management**: managing roles for internal and external users. All external user flows live here.

The React UI lives in a separate frontend repository and talks only to this API.

## Status

**There is no application code yet.** This repository currently holds the agreed rules, procedures and templates that the backend will be built from, set up for Claude Code. There is no `pom.xml`, no `src/` and nothing to run.

The decisions recorded here are real and should be followed when the code is written. Decisions still to be made are in `docs/open-questions.md`.

## What the backend will do

An operator enters a request in the UI. This API then:

1. Manages the user's **roles** in **OpenDJ (LDAP)**, the system of record for roles.
2. Stores **user details and provisioning records** in the **Futures Database** (an Oracle database in ROSA).
3. Writes an **audit record** for every action, success or failure, as single-line JSON to a local file that is rotated daily and shipped to **AWS S3**. Logs are kept for a maximum of 6 months.

```
React UI (separate repo) --HTTPS--> This API --> OpenDJ (LDAP)        user roles
                                             |-> Futures Database     user details and provisioning
                                             `-> Local log file --daily--> AWS S3   audit log
```

## Planned stack

| Area | Technology |
|---|---|
| Language and framework | Java 25 (LTS), Spring Boot 4.1.x, Maven |
| Roles | OpenDJ, through Spring LDAP |
| User details and provisioning | Futures Database (Oracle), through Spring Data JPA |
| Audit log | SLF4J, Logback and Logstash Logback Encoder; daily file shipped to S3 |
| Authentication | Okta (OIDC); this API is an OAuth2 resource server |
| API contract | OpenAPI, generated from the code with springdoc-openapi 3.x |
| Delivery | GitHub Actions, ROSA (OpenShift), Argo CD |

## Key rules

- **Operator roles:** `admin`, `editor` and `viewer`, from Okta. A `viewer` is read-only and gets `403` on anything that creates, changes or removes. What `admin` and `editor` may each do is still to be agreed.
- **Deny by default.** Every endpoint requires authentication and declares its allowed roles.
- **Every transaction** (create, change or remove) must carry a **JSM/Jira ticket**, and gets its own **transaction ID** generated by this API. The transaction ID is never the ticket.
- **Mandatory provisioning fields:** first name, surname, email, user identifier (U, Z or GAKWO), manager X number, job title and location, plus the user type.
- **Internal or external is decided on the server only**, from the email domain. It is never accepted from the client.
- **OpenDJ and Futures Database writes cannot share one transaction.** Provisioning is an ordered flow with compensation or a recorded failed state, and every step is audited.
- **Work test-first**, and never commit secrets or log passwords, tokens or unnecessary personal data.

`CLAUDE.md` has the full list.

## Getting started

To prepare for building the backend you will need **Java 25**, **Docker** (tests use containers for OpenDJ and the Futures Database), Git and Claude Code.

```bash
git config core.hooksPath .githooks   # once per clone: turn on the Git hooks
```

Then follow `docs/AGENT-WORKFLOW-GUIDE.md`. The first sprint sets up the project, the shared test infrastructure, Okta resource-server security, audit logging and a health endpoint.

Once the project exists, the commands will be:

| Command | What it does |
|---|---|
| `./mvnw test` | Unit and slice tests only (fast, no containers) |
| `./mvnw clean verify` | Build and all tests; also generates `openapi.json` |
| `./mvnw spring-boot:run` | Run locally |
| `./mvnw spring-boot:test-run` | Run locally against test containers |

Never point a local configuration at real LDAP, Futures Database, Okta or S3 environments.

## Open questions

Several decisions block parts of the build, including the OpenDJ and Futures Database schemas, the Okta configuration and roles claim, the `admin` and `editor` permission matrix, the write order between the two systems, and the formats of the ticket, transaction ID and user identifiers. See `docs/open-questions.md` for the full list and where each answer should be recorded.
